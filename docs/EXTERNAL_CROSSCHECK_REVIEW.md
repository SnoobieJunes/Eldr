## Executive summary

**Verdict: nothing blocks building or shipping today — the composition is structurally sound and fail-closed throughout — but the review surfaced one undocumented cryptographic divergence from Signal PQXDH and a short list of ecosystem-facing fixes needed before a second client or a real relay enters the picture.**

- **iOS 27 (Part I):** no must-fix-to-build items. CryptoKit's post-quantum surface is unchanged from 26.0, every SwiftUI/Liquid Glass API in use is current, and the app already satisfies the new scene-lifecycle hard requirement. Forward items: plan a deliberate, test-gated **swift-crypto 5.0 bump** (5.0 aligns with Xcode 27 CryptoKit and carries the CVE-2026-28815 X-Wing fix forward); iOS 27's beta `MLKEM768.OneTimePrivateKey` natively provides the consume-once discipline `PrekeyManager` hand-enforces (hard invariant 11) — adopt when the deployment floor allows; export-compliance documentation (`ITSEncryptionExportComplianceCode`) is still outstanding for TestFlight/App Store distribution.
- **Nostr (Part II):** a conforming NIP-59 **relay** handles our events without modification; conforming upstream **clients** fail closed by design (PQRC replaces NIP-44 encryption wholesale). Fix before second-client work: `pqrc-seal-v1`'s leading version byte **0x01 squats NIP-44's reserved value** (HIGH); the NIP-01 serializer over-escapes control characters, so ids for foreign events can diverge from strict verifiers; the NIP-42 AUTH event hardcodes `created_at: 0`, which real relays reject (±10-minute check); kinds 10420/10421/1420 are unregistered upstream and unprotected against claims by other projects.
- **Security architecture (Part III):** faithful Double Ratchet, fail-closed trust decisions everywhere, structurally-impossible nonce reuse, verify-before-decrypt ordering, CSPRNG-backed seams, envelope-encrypted state at rest, zero payload logging. The headline finding: **PQXDH omits Signal's DH2** — the responder's identity key never enters the session secret, so a recorded handshake is recoverable from Bob's *prekey* privates alone, without his identity key. The fix is cheap (one extra X25519 leg over `ik_dh_B`, already published in the signed bundle); at minimum the divergence belongs in DEVIATIONS, since the SPEC currently presents the construction as faithful PQXDH. Second: the unbounded `processedWrapIDs` set plus unauthenticated message-request emission is a memory/spam amplification surface reachable by any network party today. Remaining items are availability, retention-window, and documentation caveats — **no fail-open trust decision, key/nonce reuse, or attacker-reachable plaintext-before-verify path was found.**

**Remediation order:** (1) change the seal version byte (or adopt NIP-44's `#`-prefix convention) before any second client consumes frozen vectors; (2) add the DH2-equivalent leg to PQXDH or record the deviation explicitly; (3) bound/LRU `processedWrapIDs` and rate-limit message requests per sender; (4) inject the `Clock` seam into the NIP-42 AUTH event and tighten the simulator to upstream semantics; (5) match the NIP-01 escape letter and freeze a control-character vector; (6) upstream NIP-XX (or at least a kind-registry PR) to protect 10420/10421; (7) file export compliance; (8) schedule the swift-crypto 5.0 bump and track `MLKEM768.OneTimePrivateKey` adoption.

### Findings

**[HIGH] Plan the swift-crypto 5.0 transition before tracking iOS 27 CryptoKit parity.** The core packages' PQ surface (`MLKEM768` seed init, `decapsulate`) is identical in CryptoKit 26.0 and the 27 beta, but upstream swift-crypto has already cut `5.0.0-beta.1` explicitly to "align with CryptoKit APIs from Xcode 27 beta 1" (https://github.com/apple/swift-crypto/releases). Our `from: "4.3.1"` ranges (`Packages/PQRCCore/Package.swift:14`, `Packages/PQRCNostr/Package.swift:13`) will never auto-cross the major boundary, so the build is safe — but new 27-era types (one-time KEM keys) will land only in 5.x. Action: schedule a deliberate, test-gated bump to 5.0 GA; re-verify the CVE-2026-28815 fix is carried forward (it is a 4.3.1+ fix, so any 5.x includes it).

**[MEDIUM] iOS 27 provides natively what `PrekeyManager` hand-implements: consume-once KEM private keys.** The 27 beta SDK adds `KEMOneTimePrivateKey` (protocol, Beta) and `MLKEM768.OneTimePrivateKey` (Beta) — single-use decapsulation keys (https://developer.apple.com/tutorials/data/documentation/cryptokit.json, .../mlkem768.json). PQRC's hard invariant 11 (one-time PQ prekey private halves deleted on consumption) is currently enforced manually in `Packages/PQRCCore/Sources/PQRCCore/Prekeys/PrekeyManager.swift:27,98` (dictionary removal). Not adoptable while deployment target is 26.0 without `@available(iOS 27, *)` guards, and the core package consumes swift-crypto (needs 5.x). Action: track for adoption; it converts a tested-but-manual deletion discipline into a type-system guarantee. Nothing else we hand-compose became native: there is still no PQXDH, no Double Ratchet, no secp256k1, and no raw-ChaCha20 in CryptoKit (topic list verified), and no SLH-DSA (absent from the framework index). ML-DSA-65/87 and `SecureEnclave.MLDSA65` have existed since 26.0 — relevant to future SPEC revisions (PQ identity signatures), not to v1 conformance.

**[MEDIUM] Export compliance is declared but not completed.** `ITSAppUsesNonExemptEncryption = YES` (`App/PQRC.xcodeproj/project.pbxproj:334,364`) is the **correct, honest value** for an E2EE messenger composing its own protocol from standard primitives — E2EE messaging crypto is not in the exempt set (authentication-only / OS-provided / DRM). Per Apple, YES means App Store Connect expects export-compliance documentation, and `ITSEncryptionExportComplianceCode` should accompany it once Apple reviews the docs (https://developer.apple.com/tutorials/data/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption.json). That key is absent (expected pre-review, but it blocks streamlined TestFlight/App Store distribution). Action: file the US self-classification report / Apple export questionnaire, then add the compliance code. Note the repo's `TESTFLIGHT-GUIDE.md` should reflect this.

**[LOW] Xcode 27 toolchain (Swift 6.4) is low-risk for this project, with two watch items.** (1) Known 6.3.x-era compiler regressions involve `-default-isolation MainActor` / approachable concurrency (https://github.com/swiftlang/swift/issues/88173, /issues/89214); this project sets neither (`SWIFT_DEFAULT_ACTOR_ISOLATION` absent from pbxproj; packages set only `.swiftLanguageMode(.v6)`), and actor-owned state (e.g. `LocalRelaySimulator`, `LocalBlossomSimulator` actors) is explicit, so exposure is minimal. (2) Xcode 27 drops Intel Macs and removes ld64 (search snippet of https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes; page body unrenderable — secondary confirmation via DevelopersIO). No project setting references `-ld_classic`. Must-fix-to-build items found: **none**.

**[LOW] FoundationModels: re-validate prompts against the 27 model version; keep Private Cloud Compute out.** The framework API we call is stable, but Apple documents distinct on-device model versions ("two model versions align with OS versions 26.0–26.3 and 26.4+", https://developer.apple.com/tutorials/data/documentation/foundationmodels/systemlanguagemodel.json) and ships "updating-prompts-for-new-model-versions" guidance. `FoundationModelsAgentProvider.swift:29–53` uses raw string prompts with no `GenerationOptions` and parses a sentinel (`PASS`, line 55) — sentinel-parsing is exactly the pattern that drifts across model versions; the new `@Generable` guided generation would make `threadTurn`'s pass/contribute decision structural. Also note the 27-beta `PrivateCloudComputeLanguageModel` + `com.apple.developer.private-cloud-compute` entitlement: under the cardinal privacy rule this must remain unadopted or strictly opt-in alongside the Anthropic provider; flag in DEVIATIONS when the 27 SDK is adopted.

**[INFO] Liquid Glass / UI status.** The app already uses real glass APIs (`.glassEffect()` ×2) and standard system components; it never set `UIDesignRequiresCompatibility`, which iOS 27 now ignores (https://dev.classmethod.jp/en/articles/ios27-xcode27-migration-preparation-guide/). New 27 toolbar/glass APIs (`buttonStyle(.glass)`, `ToolbarSpacer`, `scrollEdgeEffectStyle`) are cosmetic adoptions only. ### Findings

**[HIGH] `pqrc-seal-v1` squats on NIP-44's reserved version byte 0x01.** NIP-44 v2 payloads begin with version `0x02`, and versions `0x00`/`0x01` are explicitly "reserved or deprecated"; unknown future versions are to be signaled with a leading `#` (https://raw.githubusercontent.com/nostr-protocol/nips/master/44.md). Our seal/wrap content (`SealCipher.swift:45`, `payload = 0x01 ‖ nonce(12) ‖ ct ‖ tag`) lives exactly where ecosystem clients expect NIP-44 ciphertext (kind-13/1059 `content`), so a conforming NIP-17 client will base64-decode, read version 1, and report "deprecated/unsupported version". That is fail-closed (no mis-decryption is possible — good), but it makes PQRC payloads indistinguishable from broken legacy NIP-44 v1 data and occupies a reserved value in someone else's versioning namespace. Since `docs/NIP-XX-pqrc.md:239` says interop is deferred anyway, recommend either a distinct leading marker (e.g. `#pqrc1` per NIP-44's own unsupported-version convention) or a version byte ≥ 0x80, before vectors are consumed by a second client. Deliberate and documented (`[upstream-NIP]` in DEVIATIONS), hence 🟡 not ❌ in the matrix — but the byte choice itself should change.

**[MEDIUM] NIP-01 canonical-serialization divergence for raw control characters.** NIP-01 mandates exactly seven escapes and says **"all other characters must be included verbatim"** (https://raw.githubusercontent.com/nostr-protocol/nips/master/01.md). `NostrJSON.string` (`NostrEvent.swift:80–84`) additionally escapes 0x00–0x07, 0x0B, 0x0E–0x1F as `\u%04x`. For every event PQRC itself publishes the divergence is unreachable (content is base64/hex/JSON-encoded text — no raw control chars), but when *verifying foreign events* whose content carries a raw control byte, `computedID()` produces a different id → `hasValidID()` false → valid upstream events rejected (and our ids for such content would be rejected by strict verifiers). Mitigating nuance: the de-facto JS ecosystem (`JSON.stringify`) also emits `\u00XX` escapes, so reality is split; the NIP text is nonetheless unambiguous. Recommend matching the NIP letter and adding a frozen vector with an embedded control character. No conformance test covers this today (no escape-related cases found in `Packages/PQRCNostr/Tests/PQRCNostrTests/ConformanceSuite.swift`).

**[MEDIUM] NIP-42 AUTH event would be rejected by real relays: `created_at: 0`.** NIP-42 requires the auth event's `created_at` to be current, with relays checking ~±10 minutes (https://raw.githubusercontent.com/nostr-protocol/nips/master/42.md). `LocalRelaySimulator.swift:255` hardcodes `createdAt: 0`, and the simulator's `verifyAuth` (lines 80–88) checks only challenge + signature — so the test suite cannot catch it (this also makes the simulator laxer than upstream: it validates neither the `relay` tag nor the timestamp). Harmless today because the only transport is the simulator, but the AUTH-event construction is the code a real WebSocket transport will reuse. Fix by injecting the existing `Clock` seam; tighten the simulator to upstream semantics.

**[MEDIUM] Kinds 10420 / 10421 / 1420 are unregistered upstream — no collision today, but unprotected.** Verified against the current kind registry (https://raw.githubusercontent.com/nostr-protocol/nips/master/README.md): the 10000-range table jumps 10312→(end) with 10420/10421 unclaimed, the 1000-range shows nothing at 1420, and range semantics (replaceable for 10420/10421) are correct for replace-on-update publication. Adjacent prior art exists (10050 DM relays; 10051 Marmot KeyPackage relays — a PQ-MLS messenger occupying the same neighborhood). Until NIP-XX is upstreamed, any other project can claim these numbers; kind 1420 additionally never touches a relay (rumor-only), so its number is purely internal — note NIP-17 uses kind 14 for the same role, a deliberate, documented divergence. Action: submit the NIP (or at minimum a registry PR) before second-client work freezes the numbers.

**[MEDIUM] Silent dependencies on relay behavior upstream does not guarantee.** Three instances: (1) NIP-17 makes AUTH-gated serving of kind 1059 a **SHOULD**; `docs/NIP-XX-pqrc.md:255–257` upgrades it to MUST for anchor relays — correct privacy posture, but public-relay deployments degrade to "anyone can fetch wraps" (metadata: recipient p-tag and traffic volume; THREAT_MODEL already owns IP/p-tag honesty). (2) Replaceable-event retention: NIP-01 only defines that relays *keep the latest*; nothing guarantees timely cross-relay convergence of a re-published 10421 after one-time-prekey consumption, so initiators can consume already-spent `otp`/`otp_pq` entries from stale relays — handled cryptographically by fallback (invariant 11) but worth an explicit NIP-XX note. (3) Max event size: a 64 KB padded bucket becomes ≈117 KB of wrap JSON after two base64 layers (`Padding` bucket 65536 → ciphertext 65556 → seal base64 ≈ 87 KB → wrap base64 ≈ 117 KB); many public relays cap events well below 1 MB and some below 128 KB. NIP-XX §10's `max_content_length ≥ 1 MB` requirement is the right mitigation but is a bespoke relay requirement, not an upstream guarantee — flag in THREAT_MODEL/DEVIATIONS as a deployment constraint.

**[LOW] Kind-10420 tags are plaintext protocol metadata.** `identity_key`, `agent_key`, `binding_sig`, `pqrc_capabilities` (`PQRCEvents.swift:22–27`) are multi-letter tags — correctly **not** relay-indexed per NIP-01 single-letter rules — but they publicly advertise "this npub runs PQRC and has a bound AI agent key". This is inherent to a discovery binding and presumably accepted in THREAT_MODEL; noting it here because upstream clients/relays can read (if not index) it, and `pqrc_capabilities` (`"pqxdh", "double-ratchet", "ml-kem-768"`) additionally fingerprints client capability sets across versions.

**[LOW] Blossom pointer format is not BUD-conformant yet.** BUD-01 addresses blobs as `GET https://<server>/<sha256>` and BUD-04 mirrors server-side via `PUT /mirror`; BUD-11 defines kind-24242 authorization (https://github.com/hzrd149/blossom). Our `ContentPointer.blossomURL` is the relative string `"blossom/<hash>"` (`LocalBlossomSimulator.swift` BlobCipher) with client-push mirroring and no auth event. Content-addressing, sha256 verification-on-read, and mirror fallback semantics all match the BUD model, and the pointer travels only inside the encrypted rumor — so this is invisible to today's tests, but a second client or real Blossom server needs absolute BUD-01 URLs and BUD-11 auth. Tag `[tech-debt]` in DEVIATIONS.

**[INFO] Interop verdict.** A conforming NIP-59 relay handles our events without modification: the wrap is a structurally valid kind-1059 event (valid id/sig under the ephemeral key, single p-tag, past-dated `created_at` within the blessed 2-day window — strict `created_at` relay policies accept past-dating per NIP-59's own guidance). A conforming NIP-17/59 **client** can unwrap nothing: it will decode the seal content, hit version byte 0x01, and stop — fail-closed, by design, since PQRC replaces NIP-44 encryption wholesale. The only strict-validation risks found are the AUTH timestamp (above) and event size at relays with small content caps.

### Structural comparison vs reference constructions

**PQXDH (vs signal.org/docs/specifications/pqxdh).** Signal computes `SK = KDF(DH1 ‖ DH2 ‖ DH3 [‖ DH4] ‖ SS)` with `DH1 = DH(IK_A, SPK_B)`, **`DH2 = DH(EK_A, IK_B)`**, `DH3 = DH(EK_A, SPK_B)`, `DH4 = DH(EK_A, OPK_B)`. PQRC (`PQXDH.swift:66-94`, matching `SPEC.md §4.2`) computes `dh1 = X25519(ik_dh_A, spk_B)`, `dh2 = X25519(ek_A, spk_B)`, `dh3 = X25519(ek_A, otp_B)`, `ss = MLKEM768.Encaps(otp_pq_B|pqpk_B)`. Mapping: PQRC's dh1/dh2/dh3 = Signal's **DH1/DH3/DH4**. **Signal's DH2 — the only leg that mixes the responder's identity key into the secret — has no analogue.** See Finding [M1]. Positives that *do* match the reference: the KEM SS is concatenated directly into the KDF (`PQXDH.swift:186`); ML-KEM-768 (FIPS 203) binds its own encapsulation key into the shared secret via the FO transform, so Signal's "append EncodeKEM(PQPK_B) to AD" requirement is satisfied intrinsically — no separate ciphertext binding needed; signed prekeys are verified **before** use (`PQRCMessenger.swift:162`, `PrekeyBundle.verifySignatures` → `establishSession`); both identity pubkeys are bound into the KDF `info` (`PQXDH.swift:188-190`).

**Double Ratchet (vs signal.org/docs/specifications/doubleratchet).** Faithful: `KDF_RK = HKDF(salt=rk, ikm=dh, info)` split 32/32 (`:336-346`); `KDF_CK` = HMAC(ck,0x01)/HMAC(ck,0x02) (`:349-353`); DH step on new remote key does recv-half then fresh-dhs send-half (`:188-215`); `pn/n` reset correctly; replay rejected at `n < nr` (`:161-163`); skipped keys bounded at `MAX_SKIP=1000`, keyed by `(ratchet pubkey, n)`, deleted on use (`:299-331`); message keys single-use with HKDF-derived, never-transmitted nonce (the Signal pattern). The value-semantics decrypt-on-copy/commit-on-success (`PQRCSession.swift:146-151`) is load-bearing and **correctly prevents** mis-cached skipped keys from corrupting live state when a message would cross an unapplied rekey — several reorder-across-boundary cases were traced and the failed attempt is always discarded.

**PQ rekey (PQ3 pattern, N6/N7).** Divergence from `SPEC.md §6.2`'s eager fold, formalized in `NIP-XX §6` and DEVIATIONS N6/N7. Desync reasoning: the immediate **chain refresh** is bound to the exact `(dh, n)` in the header and domain-separated by the sender's `ctr` (`:277-295`), so both sides refresh the same chain at the same position. The **deferred root fold** (`:188-229`) ties each `ss` to a specific DH output (sender folds before its next send-half; receiver before that chain's recv-half), so even under crossing rekeys each fold is inserted at the *same* point of the linear root chain on both sides — order is determined by the observed ping-pong, not by local arrival, so HKDF non-commutativity does not cause divergence. N8 counter (`messagesSinceRekey` counts both directions) and `peerRekeyCounter` anti-regression (`:267`) are consistent. The 8-deep KEM history (`:37-38,243-245`) is bounded and dropped references are ARC-freed; it modestly widens the post-compromise window (a device compromise yields up to 8 KEM decap keys) — see [L2].

### Findings

**[Medium] M1 — PQXDH drops Signal's DH2; responder identity key is never a secret input to SK.** `PQXDH.swift:96-101,161-166`; `SPEC.md §4.2`. Every leg of SK rests on Bob's *medium-term* prekeys (spk/otp/pqpk) — none on his long-term identity key. **Attacker gain:** an adversary who passively records a handshake and later obtains Bob's prekey private halves (spk + the KEM private), *without* his identity key, can derive SK — a session-key recovery that Signal's DH2 specifically prevents. It also means the PQXDH key agreement is not self-authenticating for the responder (authentication is carried by the prekey signatures + the gift-wrap seal instead). **Reachability:** every handshake. **Mitigations that lower real-world impact:** single-device design co-locates all keys in the same Keychain/SE (compromising prekeys usually means compromising identity too), and prekey privates are currently not even persisted across launches (DEVIATIONS T2). But the divergence is **undocumented** — SPEC/DEVIATIONS present this as faithful "Signal PQXDH / Apple PQ3" — and the property matters more once T2 is fixed for the network transport. **Fix (cheap):** Bob's `ik_dh_B` is already published and identity-signed in the bundle, so add `dh_idB = X25519(ek_A, ik_dh_B)` to the IKM to restore the DH2 binding; record the choice in DEVIATIONS either way.

**[Medium] M2 — Unbounded `processedWrapIDs` set + unauthenticated message-request amplification.** `PQRCMessenger.swift:62,274-282,285-294`. Anyone can ChaChaPoly-seal a gift wrap to the recipient's *public* Nostr key; `GiftWrap.unwrap` succeeds (the attacker signs their own seal and matches `rumor.pubkey == seal.pubkey`), so each junk envelope is inserted into the in-memory `processedWrapIDs` (never bounded) and yields a `.messageRequest` (`:289`). **Attacker gain:** unbounded memory growth and message-request spam from a network party with no session and no contact relationship; the anchor-relay AUTH gate (`LocalRelaySimulator.visible:156-164`) helps, but SPEC §9 keeps public relays as a fallback that does not gate. **Fix:** size-bound/LRU the dedup set (the app has a persisted `ProcessedEventModel`, but the package set is separate and unbounded), and rate-limit/coalesce message requests per sender pubkey.

**[Low] L1 — Handshake `ik_dh`/`ek` are not checked against the peer's signed bundle; handshake authentication rests entirely on the gift-wrap seal.** `PQRCMessenger.swift:306-316` only checks `handshake.ik == contact.binding.identityPubkey`; DEVIATIONS T8 confirms `ik_dh` is not cross-checked. This is **safe today** because `processUnwrapped` attributes the sender from the *seal signature* (verified Nostr key → verified contact) before the handshake is processed, so substituting `ik_dh`/`ek` requires the contact's Nostr key. **Risk is forward-looking:** the planned BLE/Multipeer local link (SPEC §10, S1) is documented to deliver "the same ratchet ciphertext, no gift wrap" — without the seal, dh1's binding is vacuous (Bob never verifies `ik_dh` belongs to the claimed identity) and an active attacker on that link could impersonate a contact during handshake. **Fix:** verify `handshake.ikDH` against the peer's verified bundle `ik_dh` (and bind `ik_dh` into the kind-10420 assertion, as T8 queues); require sender authentication on any non-gift-wrapped transport.

**[Low] L2 — 8-generation KEM key retention widens the post-compromise window.** `DoubleRatchet.swift:37-38,243-245,257`. Retaining up to 8 KEM private keys (to absorb rekeys that crossed the receiver's own rotations, N7) means a device compromise yields up to 8 decap keys; rekeys still targeting any of them remain decryptable. Bounded and justified by chaos resilience, and stale keys are ARC-freed when evicted, but it is a deliberate, small PCS reduction. **Fix:** document in THREAT_MODEL; consider whether the bound can be lowered, and that 8 generations ≈ 400 messages of tolerated peer lag.

**[Low] L3 — Rekey-carrying message is a single point of failure for the chain (loss-tolerance regression vs vanilla DR).** `DoubleRatchet.swift:117-137,277-295`; retry queue `PQRCMessenger.swift:408-419`. Because the chain refresh and every subsequent message key depend on the KEM ciphertext carried *only* in the rekey message, permanent loss of that one message wedges all later messages (held in the 256-bounded retry queue until overflow → quarantine). Vanilla DR tolerates single-message loss via skipped keys. **Mitigated** by store-and-forward relays + the 60-attempt outbox, so the chaos matrix (drop=0.1) converges (drops are retried, not permanent); a relay cannot target the rekey message because it cannot see which message carries it. Under a heavy reorder burst, >256 messages queued behind a delayed rekey can quarantine healthy traffic (N16's accepted tradeoff). Availability only, never confidentiality.

**[Low] L4 — Seal/wrap envelope layer has no forward secrecy (static sender→recipient conversation key).** `SealCipher.swift:16-34`. The seal key is `HKDF(ECDH(sender_nostr_priv, recipient_nostr_pub))`, never rotated — consistent with NIP-44/NIP-59, so not a divergence, but worth stating: compromise of a recipient's Nostr private key lets an attacker decrypt all recorded seals addressed to them, **linking sender↔recipient** and exposing ratchet headers for past traffic (message *plaintext* stays protected by the inner ratchet's FS). The wrap layer's per-message fresh key (`GiftWrap.swift:56`) does not change this since both layers decrypt under the recipient's static Nostr key. **Fix:** make this explicit in THREAT_MODEL (sender-anonymity is not forward-secret against recipient-key compromise).

**[Info] I1 — Modulo bias in timestamp fuzzing, negligible.** `PQRCSession.swift:21-32`: `offset = value % (window+1)`. Relative bias ≈ 9e-15; irrelevant for metadata fuzzing (never key material), past-only and CSPRNG-sourced in production. No action needed.

**[Info] I2 — `SeededRandomSource` (deterministic SHA-256 stream, not a CSPRNG) is `public` in the shipping core and drives the in-app "Local Universe" demo personas.** `Seams.swift:60-92`, `LocalUniverse.swift:43-44`. Real onboarding uses `System*` sources (`PersonaRuntime.swift:58-60`), so no production crypto path is affected, but a deterministic RNG in the production module is a footgun. **Fix:** gate behind `#if DEBUG` or a test-only/demo target.

**[Info] I3 — Remote Anthropic inference sends decrypted context off-device.** `AnthropicAPIProvider.swift:21-53`. Off by default, consent-gated (D3), ephemeral `URLSession`, signing keys never leave the device, last-20-entry context only. Documented tradeoff and the sole path where plaintext leaves the device; ensure THREAT_MODEL states it plainly.

**Needs deeper analysis (exact checks to run):**
- **Crossing-rekey + multi-DH-step root sync under reorder:** the deferred folds were reasoned to stay position-synchronized, but this is the highest-complexity invariant. Add a directed test: A and B each send a rekey that crosses, *then* each performs a DH ratchet step in both orders (A-first and B-first) with the rekey messages reordered relative to the new ratchet keys; assert identical root keys via `makeSnapshot().rootKey` on both sides. The chaos matrix exercises this statistically but does not assert root-key equality at the crossing.
- **Outbox-give-up wedging:** confirm what happens to a session when `publishWithRetry` exhausts 60 attempts on a rekey-carrying message (`PQRCMessenger.swift:227-239`) — does the sender's ratchet stay ahead of the receiver permanently? Trace whether any resync path exists.
- **`processedWrapIDs` vs app `ProcessedEventModel`:** confirm the app layer bounds its persisted dedup store; the package set is definitively unbounded.

### Recommendations (prioritized)

1. **M1:** Add a DH leg over the responder's identity-DH key (`X25519(ek_A, ik_dh_B)`) to restore PQXDH's DH2 binding — the key is already in the signed bundle. If retaining the current design, record it explicitly in DEVIATIONS as a deviation from Signal PQXDH with the FS-under-prekey-compromise caveat, rather than presenting it as faithful.
2. **M2:** Bound/LRU `processedWrapIDs` and rate-limit message-request emission per sender; this is reachable by any network party today.
3. **L1:** Cross-check `handshake.ik_dh` against the verified bundle and bind `ik_dh` into kind-10420 (T8); make handshake authentication independent of the gift-wrap layer before shipping the local-link transport.
4. **L3/L4/L2:** Document the rekey-message loss-sensitivity, the envelope layer's lack of forward secrecy, and the 8-key KEM retention window in THREAT_MODEL; consider whether the KEM history bound can be reduced.
5. **I2:** Move `SeededRandomSource` out of the production surface (DEBUG-gate or test target).
6. Add the crossing-rekey root-key-equality assertion described above to convert the statistical chaos coverage into a hard invariant test.

Overall: the composition is faithful to the Double Ratchet and is carefully implemented (actor isolation, value-semantics decrypt, derived single-use nonces, bidirectional binding, fail-closed gates, no timestamps in the key schedule, envelope-encrypted state at rest, no payload logging). The one structural divergence from the named reference is the omitted PQXDH DH2 (M1); the remaining items are availability, resource-exhaustion, and documentation gaps rather than confidentiality breaks. No fail-open trust decision, key/nonce reuse, or attacker-reachable plaintext-before-verify path was found.
